# Внутренние контракты и модель событий v1

Основание — [TASK-005](PLAN.md#task-005), [источники истины](SPEC.md#источники-истины-и-сохраняемые-связи) и [модель состояний](SPEC.md#состояния-заказа-и-устойчивость-к-повторам). Имена ниже — внутренний контракт, **не предположение о названиях полей внешнего API**. Адаптер МойСклад нормализует подтверждённые ответы TASK-006–009. Публичные обработчики WordPress проверяют права, владение, серверный контекст и nonce согласно способу запроса.

Последовательность необходимых действий: (1) локально собрать точечные GET metadata/выбранных объектов без повторного полного поиска отгрузок; сохранить ID и типы защищённо; (2) менеджер подтверждает смысл решений/исполнения и выбирает два канала/услугу; (3) отдельно подготовить **конкретный** пакет отсутствующих объектов/атрибутов с телами операций, влиянием и очисткой, проверить связанные сценарии/возможные письма/чеки/деньги и получить согласование; (4) только после согласования выполнить недостающие изменения и проверить постоянные соответствия GET/контрольным сценарием; (5) настройки адаптера принимают только проверенные активные ID и отклоняют удалённые тестовые, другой склад, неизвестный тип/статус. Создание финансовых документов МойСклад и автоматизация СБИС не добавляются. Неизвестное влияние автоматизаций фиксируется прямо и не считается безопасным по имени канала.

Эта подготовка не является доказательством поддержки новых атрибутов/статусов, конкурентной обеспеченности или полноты кодов. TASK-008 остаётся незавершённой до выбора/проверки постоянных соответствий; текущие испытания документов — [EXEC-CHK-022](ACCEPTANCE.md#exec-chk-022).

`id`/связи — непрозрачные непустые строки, UUID магазина/заказа неизменяем. `schema_version=1`; версия состава заказа — целое от 1. Время — UTC epoch seconds, сроки сохраняются один раз; интерфейс отображает Europe/Moscow. Деньги — целые копейки RUB, JSON передаёт целое либо каноническую десятичную строку для границ, исключающих потерю точности. Float для суммы не применяется. НДС хранится выделенной частью включённой цены, 13 000 ₽ не увеличиваются повторно. Налоговый контракт доставки/округления подтверждается TASK-011.

Ключи идемпотентности и ID собственных операций/удержаний сравниваются по точным байтам, без приведения регистра и удаления пробелов; собственная схема v3 использует VARBINARY. Версия схемы базы независима от schema_version снимков. После миграции проверяются колонки, индексы, уникальность и InnoDB; при отказе прежняя версия сохраняется для повторного запуска.

Количества нормализуются в единицы продажи; текущая модель одежды/обуви — целые экземпляры. Если контрольный ассортимент имеет дробную единицу, TASK-006 должен явно расширить контракт и проверки, без округления остатков. Внешние ID не заменять названиями. Отсутствующее/неполное/недоступное поле обозначать `unknown`, не нулём. Идентификаторы и точные коды служебны, в публичные ответы не входят.

## Раздельные измерения состояния

### Доступ к заказам TASK-018

Технический контракт REQ-011/091–093/101/266; SPEC не изменён. `_suhoput_origin=site` ставится сервером в `woocommerce_checkout_create_order`, customer_id берётся из авторизованной сессии. Адаптер не создаёт историю из внешних/ручных документов и не ставит этот признак при импорте. При TASK-025 проверить полный checkout: контроль hook не заменяет приёмку оформления.

История/страница/API требуют site-origin + точного customer_id; email, имя, телефон, контрагент и оптовое право не доказывают владение. Все зарегистрированные WooCommerce статусы включаются; отключение оптового доступа сохраняет историю. Управленческий WC REST API требует manage_woocommerce; собственный GET `/suhoput/v1/orders` и `/orders/{id}` выдаёт только id/number/status/total/currency/created_at. View-order/order-received/order-pay, pay POST, tracking и Store API order/{id}/checkout/{id} проверяют владельца. Несовпадающий id в query/body/JSON Store API отклоняется до штатного обработчика. Ответы получают private/no-store и Vary Cookie/Authorization; production-кеш ещё проверяется TASK-019/040/048.

Гостевое доказательство: почта самого заказа, 256-битное случайное подтверждение, срок 30 минут, один заказ, purpose=view/claim, хеш браузерного cookie и user_id получателя привязки. Запрос требует nonce и браузер; повтор не чаще 60 секунд на заказ. Ответ одинаков при неверном ID/email/неподходящем заказе. GET ссылки только показывает форму; POST с nonce атомарно меняет issued→used. Использованное, истёкшее, заменённое подтверждение, другой браузер/заказ/purpose/аккаунт либо изменившийся email заказа отвергаются. При смене устройства нужно новое письмо в новом браузере.

View открывает данный гостевой заказ в браузере на 60 минут без перечисления истории. Claim требует авторизованного аккаунта из запроса и нового письма, меняет customer_id через CRUD и закрывает прежний гостевой доступ. Потребление сохраняется до CRUD-эффекта; при неизвестном/неуспешном сохранении старое подтверждение не повторяется, нужен новый запрос после проверки состояния. Пароли/сессии остаются штатными WordPress. Cookie HttpOnly/SameSite=Lax передаётся Secure при HTTPS; сырой токен не хранится в собственных таблицах и не включается в API/отчёт. Только доверенный исходный checkout-hook выдаёт первый браузерный доступ без письма; чужой order key/email не заменяют его.

Штатный статус WooCommerce — отображение, не единственное поле модели. Сборка разрешается при успешной розничной оплате и полном подтверждённом резерве; для опта — актуальном подтверждении состава и полном резерве. Оптовое подтверждение никогда не вызывает payment_complete. Изменение оплаченного состава — расхождение; замена через связанный возврат и новый заказ.

Дедупликация уведомления: order_uuid + composition_version + переход + тип + адресат; смена трека добавляет версию отправления. Внешняя операция: provider + operation_id уникальна; входящее событие имеет проверенный ID либо детерминированный хеш существенных полей. Конкретные ограничения/миграции — TASK-012–013.

Политики [ReservePolicy](../wp-content/plugins/suhoput-core/src/Domain/ReservePolicy.php), [Money](../wp-content/plugins/suhoput-core/src/Domain/Money.php), [Availability](../wp-content/plugins/suhoput-core/src/Domain/Availability.php) и [OperationResult](../wp-content/plugins/suhoput-core/src/Domain/OperationResult.php) проверяются на имитациях через tests/contracts.php. Это модель решений, не обработчик внешних операций и не доказательство гонок с другим каналом. Реальные переходы, журнал, блокировки, версии, UI и письма выполняются зависимыми задачами.

## Нормализация МойСклад remap/1.2

### Исполнение сохранённых команд

`OrderOutbox::save(WC_Order, command)` вызывается серверным оформлением для уже сохранённого заказа. command содержит operation_id, order_id, composition_version, provider, action, idempotency_key, request (снимок/locator/ожидаемый результат внутри неизменного запроса). Срок резерва сохраняется в снимке один раз; восстановление его не рассчитывает заново. `_suhoput_commands` — закрытые CRUD-метаданные, не публичный API. Прямая запись из клиентского запроса недопустима. `synchronize`/порционный `recover` восстанавливают журнал и сигнализируют готовность; потеря сигнала не теряет данные.

`Worker::operation(provider, action, send, reconcile, apply)` регистрирует одного исполнителя. send/reconcile получают сохранённую строку и декодированный request и возвращают OperationResult. Unknown никогда не вызывает send повторно. apply получает строку/результат и выполняет только повторяемую локальную проекцию: CRUD по устойчивому ID, монотонное состояние, уведомления через Journal::notify; внешние действия требуют отдельной команды. `applied_at` фиксируется после проекции. `Worker::event(provider, verify, apply)` проверяет актуальный внешний объект и его связь с сохранённым order_id; null означает недоступную сверку. Применённое событие получает processed_at, повтор пропускается. HTTP-адаптер обязан проверить подлинность/связь перед receive и вернуть ACK только после успешного возврата; HTTP endpoint добавляется задачей конкретной интеграции. `notifications(send, reconcile)` имеет отдельный журнал доставки; при unknown доступна только сверка. Это интерфейсы исполнения, действующих внешних адаптеров пока нет.

Схема v4 добавляет отметку проекции операции, связь/попытки/сроки/окончание inbox и lease/result уведомлений. Схема v5 добавляет available_at и retry_count; снимок остаётся версии 1. Канонический запрос сохраняется полностью; секретные заголовки не включаются.

### Исполнение по системной минуте

При ошибке периодической работы нижняя граница retry сначала сохраняется отдельным pending AS action, затем в опциях. Если запись опций отказала, следующий процесс также читает время pending retry и не обходит Retry-After; ошибка сохранения явно прерывает обработчик. Двойной отказ всех долговечных хранилищ требует восстановления базы/очереди, а не объявления успешного завершения.

Адаптеры регистрируются на `suhoput_register_workers(Worker, Scheduler)` после init Action Scheduler. `Scheduler::periodic(name, catalog|photos, interval, callable)` задаёт уникальную периодическую работу; interval ≥60 секунд, обмен цен/остатков использует 300. Callback обязан быть повторяемым с контрольной точкой. `RetryLater(seconds)` передаёт разобранный Retry-After 1…86400 секунд без секретных заголовков и текста ответа. Отправка и read-сверка уведомления/операции одинаково сохраняют эту задержку. Unknown всегда остаётся read-сверкой.

Для исходного срока команда сохраняет `not_before` в UTC epoch seconds; повтор не меняет его и не продлевает резерв. Это техническая нижняя граница запуска, а не автоматическая отмена заказа. Бизнес-обработчик под блокировкой проверяет актуальную версию, состояние связанного действия и подтверждённые факты перед истечением/переходом (TASK-027–029); отсутствие такой проверки не разрешает зависимую операцию. Backoff 60/120/240…3600 секунд и минимум Retry-After сохраняются в next_attempt_at. После аварии журнал восстанавливает AS-индекс, а expired lease не снимает владение живого соединения. Периодическая ошибка/следующая попытка/последний успех сохраняются в закрытых опциях; очистка AS не заменяет сверку внешних результатов. Критическая задержка ≥10 минут или ≥8 неуспешных запусков сохраняет дедуплицированное намерение уведомить менеджера. Реальные уведомления и интерфейс относятся к TASK-038/039/046.

[Официальное описание товара](https://raw.githubusercontent.com/moysklad/api-remap-1.2-doc/master/md/dictionaries/_product.md) задаёт единицы цены. [Описание модификации](https://raw.githubusercontent.com/moysklad/api-remap-1.2-doc/master/md/dictionaries/_variant.md) указывает, что при отсутствии собственной цены в ответе выводится цена родителя. Это объяснение протокола; одинаковые значения родителя и варианта не доказывают происхождение конкретной цены без контрольного сценария. Реальный контроль 08.10.2026, remap/1.2, EXEC-CHK-021: вариант без собственных цен следует за изменением родителя 1300000/1200000 → 1500000/1350000 коп.; собственные 1400000/1250000 сохраняются. Переданный ноль розничной цены возвращается API как цена родителя. PUT `salePrices: []` оставляет собственные цены; PUT двух выбранных цен со значением 0 снимает их, после чего GET возвращает цены родителя. Чтение даёт эффективную цену, происхождение нулевого ввода из этого ответа не восстановить. Нормализовать отдельно каждый выбранный тип, проверять положительность **полученного значения**, RUB и копейки; не объявлять API-ответ нулевым, когда он содержит эффективную положительную цену. WooCommerce/чек в этом внешнем испытании не участвовали.

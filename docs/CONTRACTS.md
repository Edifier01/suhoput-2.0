# Внутренние контракты и модель событий v1

Основание — [TASK-005](PLAN.md#task-005), [источники истины](SPEC.md#источники-истины-и-сохраняемые-связи) и [модель состояний](SPEC.md#состояния-заказа-и-устойчивость-к-повторам). Имена ниже — внутренний контракт, **не предположение о названиях полей внешнего API**. Адаптер МойСклад нормализует подтверждённые ответы TASK-006–009. Публичные обработчики WordPress проверяют права, владение, серверный контекст и nonce согласно способу запроса.

## Общие типы

`id`/связи — непрозрачные непустые строки, UUID магазина/заказа неизменяем. `schema_version=1`; версия состава заказа — целое от 1. Время — UTC epoch seconds, сроки сохраняются один раз; интерфейс отображает Europe/Moscow. Деньги — целые копейки RUB, JSON передаёт целое либо каноническую десятичную строку для границ, исключающих потерю точности. Float для суммы не применяется. НДС хранится выделенной частью включённой цены, 13 000 ₽ не увеличиваются повторно. Налоговый контракт доставки/округления подтверждается TASK-011.

Ключи идемпотентности и ID собственных операций/удержаний сравниваются по точным байтам, без приведения регистра и удаления пробелов; собственная схема v3 использует VARBINARY. Версия схемы базы независима от schema_version снимков. После миграции проверяются колонки, индексы, уникальность и InnoDB; при отказе прежняя версия сохраняется для повторного запуска.

Количества нормализуются в единицы продажи; текущая модель одежды/обуви — целые экземпляры. Если контрольный ассортимент имеет дробную единицу, TASK-006 должен явно расширить контракт и проверки, без округления остатков. Внешние ID не заменять названиями. Отсутствующее/неполное/недоступное поле обозначать `unknown`, не нулём. Идентификаторы и точные коды служебны, в публичные ответы не входят.

При несовместимой смене формата создать новую schema_version и миграцию; не переинтерпретировать старый оплаченный снимок. canonical_request сохраняется вместе с SHA-256 после детерминированной сериализации; хеш не заменяет исходное содержимое. Секретные заголовки не входят в canonical_request. Персональные данные защищаются правами/целевым хранением и сроками TASK-042.

## Раздельные измерения состояния

| Измерение | Значения модели | Источник истины |
| --- | --- | --- |
| Контекст | retail, wholesale | Серверное право покупателя в момент снимка |
| Оптовое решение | unconfirmed, confirmed, rejected, canceled, unknown | Актуальный связанный документ МойСклад; unknown при невозможности свежей проверки |
| Оплата | none, pending, succeeded, canceled, unknown, waiting_for_capture | Проверенные попытки провайдера; факт succeeded монотонен, возвраты отдельны |
| Исполнение | awaiting_exchange, awaiting_reserve, awaiting_payment, ready, packing, shipped, manager_required, canceled | Core на проверенных внешних событиях; shipped может отражать фактическую несогласованную отгрузку с расхождением |
| Резерв | none, acquiring, confirmed, releasing, released, unknown | Единственный исполнитель Core + подтверждённый результат МойСклад |
| Доставка | none, tracked, in_transit, at_point, delivered, returning, returned, unknown | Проверенная история перевозчика и направление; ручное уточнение с основанием |
| Обмен | queued, running, confirmed, refused, unknown | Журнал операций |
| Возврат денег/чек/складской возврат/маркировка | Собственные операции с confirmed/refused/unknown | Один исполнитель каждого действия, независимые результаты |

Штатный статус WooCommerce — отображение, не единственное поле модели. Сборка разрешается при успешной розничной оплате и полном подтверждённом резерве; для опта — актуальном подтверждении состава и полном резерве. Оптовое подтверждение никогда не вызывает payment_complete. Изменение оплаченного состава — расхождение; замена через связанный возврат и новый заказ.

## События и единственный исполнитель

| Событие | Данные / исполнитель | Результат / резерв / уведомление |
| --- | --- | --- |
| Сохранение оформления | Заказ CRUD, UUID, снимок и первая запись / Core | Задание обмена, ожидает подтверждения полного резерва; срок retail +3600 от первой записи, wholesale +86400 от отправки заявки, повтор не продлевает |
| Полный резерв подтверждён | Подтверждённая операция и текущая версия / Core | Розница ожидает оплаты до срока; опт на согласовании. Удержание уже отражённого количества не вычитается снова |
| Успешная оплата | Связь, сумма, валюта, свежий статус / платёжный адаптер → Core | Факт оплаты сохраняется; если резерв снят, запустить проверку наличия/полного повторного резерва. Уведомление один раз |
| Истечение retail без попыток/все canceled | Все попытки и неизвестные создания проверены / Core | Снять резерв отдельной командой; отмена и письмо только после confirmed снятия |
| Истечение retail, confirmed pending | Проверены все попытки / Core | Снять резерв, новые попытки закрыты, прежнюю продолжать сверять; не объявлять отказ платежа |
| Unknown платежа/создания/снятия | Журнал и свежая сверка / Core | Техническое ожидание, без новой попытки поверх unknown и без недоказанной отмены; менеджеру проблема |
| waiting_for_capture | Проверенный неожиданный статус / Core | Техническое ожидание, без автоматического capture/сборки; менеджеру разбор |
| Поздний succeeded, все позиции доступны | Свежий выбранный склад / Core → MS | Полный повторный резерв, сборка только после confirmed; повторная оплата не нужна |
| Поздний succeeded, нехватка | Доказанная нехватка / Core | Оплата сохранена, manager_required, уведомить покупателя/менеджера; без автоматического возврата |
| Поздний succeeded, API неизвестен | Unknown сверки/резерва / Core | Техническое ожидание и сверка; неизвестное не показывать как нехватку |
| Подтверждение wholesale до снятия | Актуальное решение и версия / Core | Резерв сохраняется, первоначальный таймер больше не снимает; уведомить без online-оплаты |
| Отклонение/отмена wholesale | Актуальное решение / Core → MS | Снять оставшийся резерв, уведомить на подтверждённом переходе |
| Истечение wholesale | Свежий документ ещё unconfirmed / Core → MS | Снять, сохранить заявку expired, уведомить обе стороны; confirmed/fulfilling сохраняет резерв |
| Истечение wholesale, свежая проверка недоступна | Unknown / Core | Повтор проверки, не снимать по устаревшему локальному состоянию |
| Позднее подтверждение wholesale | Версия и свежий остаток / Core → MS | Полный повторный резерв; недостаток/unknown блокирует сборку и виден менеджеру |
| Сборка/отгрузка | Документ MS / Core | Оплата независима; фактическая отгрузка учитывается без повторного списания. Неправомерная отгрузка/изменённый оплаченный состав — расхождение |
| Трек добавлен/заменён | Менеджер с правом на заказ / Core | Сохранить и уведомить, тот же трек письма не повторяет; вручение не выводится из наличия номера |
| Вручение | Проверенное событие/направление/время / Core | Доставка delivered, фискальное событие выбранному единственному исполнителю; повтор не создаёт второй чек |
| Отказ/невручение/возврат/старое событие | История и направление / Core | Сохранить действительное состояние, менеджеру; без автоматического возврата денег/повторного чека |
| Менеджер инициировал возврат | Позиции/сумма/налог/причина, доступный остаток / Core → платёжный адаптер | Отдельное намерение, unknown сверяется, succeeded подтверждает только деньги; склад/чек/маркировка отдельны |

Дедупликация уведомления: order_uuid + composition_version + переход + тип + адресат; смена трека добавляет версию отправления. Внешняя операция: provider + operation_id уникальна; входящее событие имеет проверенный ID либо детерминированный хеш существенных полей. Конкретные ограничения/миграции — TASK-012–013.

Политики [ReservePolicy](../wp-content/plugins/suhoput-core/src/Domain/ReservePolicy.php), [Money](../wp-content/plugins/suhoput-core/src/Domain/Money.php), [Availability](../wp-content/plugins/suhoput-core/src/Domain/Availability.php) и [OperationResult](../wp-content/plugins/suhoput-core/src/Domain/OperationResult.php) проверяются на имитациях через tests/contracts.php. Это модель решений, не обработчик внешних операций и не доказательство гонок с другим каналом. Реальные переходы, журнал, блокировки, версии, UI и письма выполняются зависимыми задачами.

## Нормализация МойСклад remap/1.2

### Исполнение сохранённых команд

`OrderOutbox::save(WC_Order, command)` вызывается серверным оформлением для уже сохранённого заказа. command содержит operation_id, order_id, composition_version, provider, action, idempotency_key, request (снимок/locator/ожидаемый результат внутри неизменного запроса). Срок резерва сохраняется в снимке один раз; восстановление его не рассчитывает заново. `_suhoput_commands` — закрытые CRUD-метаданные, не публичный API. Прямая запись из клиентского запроса недопустима. `synchronize`/порционный `recover` восстанавливают журнал и сигнализируют готовность; потеря сигнала не теряет данные.

`Worker::operation(provider, action, send, reconcile, apply)` регистрирует одного исполнителя. send/reconcile получают сохранённую строку и декодированный request и возвращают OperationResult. Unknown никогда не вызывает send повторно. apply получает строку/результат и выполняет только повторяемую локальную проекцию: CRUD по устойчивому ID, монотонное состояние, уведомления через Journal::notify; внешние действия требуют отдельной команды. `applied_at` фиксируется после проекции. `Worker::event(provider, verify, apply)` проверяет актуальный внешний объект и его связь с сохранённым order_id; null означает недоступную сверку. Применённое событие получает processed_at, повтор пропускается. HTTP-адаптер обязан проверить подлинность/связь перед receive и вернуть ACK только после успешного возврата; HTTP endpoint добавляется задачей конкретной интеграции. `notifications(send, reconcile)` имеет отдельный журнал доставки; при unknown доступна только сверка. Это интерфейсы исполнения, действующих внешних адаптеров пока нет.

Схема v4 добавляет отметку проекции операции, связь/попытки/сроки/окончание inbox и lease/result уведомлений. Канонический запрос сохраняется полностью; секретные заголовки не включаются. Номер схемы снимка остаётся 1.

[Официальное описание товара](https://raw.githubusercontent.com/moysklad/api-remap-1.2-doc/master/md/dictionaries/_product.md) задаёт единицы цены. [Описание модификации](https://raw.githubusercontent.com/moysklad/api-remap-1.2-doc/master/md/dictionaries/_variant.md) указывает, что при отсутствии собственной цены в ответе выводится цена родителя. Это объяснение протокола; одинаковые значения родителя и варианта не доказывают происхождение конкретной цены без контрольного сценария. Пагинация/нормализация/импорт и возобновление проверяются раздельно.

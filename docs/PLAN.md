# Suhoput 2.0 — подробный план реализации

План утверждён владельцем в чате 08.10.2026. Описывает 11 этапов и 55 задач. Требования — [SPEC](SPEC.md), архитектура — [ARCHITECTURE](ARCHITECTURE.md), утверждённые решения — [DECISIONS](DECISIONS.md), оперативное состояние — [STATUS](STATUS.md), доказательства — [ACCEPTANCE](ACCEPTANCE.md). План не содержит оперативных отметок готовности.

## Результат и ограничения

Создать магазин по полному SPEC. Покрываются все 319 исходных групп и REQ-320–321 уточнений владельца, включая 62 строки исходной приёмки; краткие названия не сокращают исходные условия. Зависимости не образуют циклов, подключение ЮKassa зависит от всех предшествующих задач.

- Собственная классическая тема, классические корзина и оформление, два собственных плагина, WooCommerce CRUD и HPOS.
- Ручные поля сайта сохраняются при обмене. Розница и опт имеют разные права и цены, общий контур наличия и резервов.
- Розничный резерв — час от первой надёжной записи; неподтверждённый оптовый — 24 часа.
- Поздняя успешная оплата сохраняется. Нехватка требует решения менеджера; автоматического возврата нет.
- Оплаченный снимок неизменяем. Замена — связанный возврат и новый заказ.
- Полная отправка из одной точки по России. Отправления создаёт менеджер; превышение фактического тарифа покрывает продавец.
- Маркировка сканируется один раз в МойСклад; оптовый ЭДО остаётся ручным через СБИС.
- Установка, подключение и интеграционные испытания ЮKassa — только STAGE-011.
- Выпуск — GitHub Release с commit SHA и SHA-256, архив передаётся по SSH.

Действующие уточнения: [REQ-320](SPEC.md#req-320) — только выбранный учётный склад; [REQ-321](SPEC.md#req-321) — доступы по необходимости и предварительное согласование конкретных изменяющих операций. Они имеют приоритет над прежними формулировками общего пула.

## Архитектура и интерфейсы

| Область | Ответственность |
| --- | --- |
| `wp-content/themes/suhoput` | Вёрстка и состояния; без внешних API и бизнес-решений |
| `wp-content/plugins/suhoput-core` | Права, цены, состояния, резерв, журнал операций, доставка, уведомления и фискальный адаптер |
| `wp-content/plugins/suhoput-moysklad` | HTTP API, сопоставление ID, снимки, импорт и подтверждённые команды обмена |
| `infra/` | Стенд, серверные задания, выпуск, копии и восстановление |
| `tests/` | Модульные, WordPress-интеграционные, браузерные и безопасные внешние сценарии |

Локально — Docker Compose с Linux-контейнерами WordPress/PHP, MariaDB, WP-CLI и перехватчиком почты. Исходная база — PHP 8.3 и MariaDB 10.11; точные версии фиксирует TASK-003 по [WordPress](https://wordpress.org/about/requirements/) и [WooCommerce](https://woocommerce.com/document/server-requirements/), затем проверяет окружение. На VPS сначала обследовать существующую схему: совместимую сохранить; новое размещение — Nginx, PHP-FPM и MariaDB.

| Контракт | Минимальное содержание |
| --- | --- |
| Снимок товара/варианта | ID, структура, характеристики, два типа цен, физические остатки, внешние резервы, архив, время и полнота получения |
| Снимок заказа | UUID магазина/заказа, версия, контекст, позиции, количества, цены с налогом, доставка, итоги, получатель и связи |
| Команда операции | ID, заказ, версия, действие, неизменяемое тело и способ последующей сверки |
| Результат операции | confirmed / refused / unknown, внешние ID и доказательство |
| Предложение доставки | Перевозчик, услуга, пункт, отправитель, упаковки, входы расчёта, стоимость и срок актуальности |
| Событие перевозчика | Отправление, направление, исходный статус, время события/получения и подтверждённый смысл |
| Фискальные данные | Позиция, вариант, экземпляр, полный код, результаты проверки, событие и единственный исполнитель |

Точные поля API берутся из контрольных ответов. Новые обработчики проверяют права и владение данными на сервере. Заказы — только CRUD; собственные таблицы — связи, операции, входящие события, уведомления и удержания. Не изменять штатные таблицы заказов напрямую; [руководство HPOS](https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/recipe-book/).

## Исполнение и доказательства

1. До изменения файлов обновить текущую работу в STATUS.
2. Прочитать полные связанные REQ, включая условия абзацев.
3. Для бизнес-логики сначала проверяющий сценарий, затем реализация.
4. Выполнить проверки и исправить существенные замечания.
5. Записать доказательства в ACCEPTANCE, обновить затронутые документы.
6. Сохранить контрольную точку Git с допустимым автором.

Каждое доказательство содержит дату, команду/сценарий, окружение, версии, commit SHA либо отличия рабочей копии. Реальные испытания, имитации и незапущенные проверки различаются. Задачи не переходят в done до выполнения критериев и обновления документов.

Колонка REQ/CHK перечисляет требования и существующие проверки с теми же номерами. Полный источник обязателен. ID задач глобальные: не перенумеровывать и не использовать повторно. Этапы группируют результаты; независимые задачи могут начаться раньше соседних этапов после собственных зависимостей. Передача следующей задаче — подтверждённый результат и интерфейсы; подробные протоколы связаны с ACCEPTANCE.

## Обязательные сценарии проверки

| Набор | Минимальные сценарии |
| --- | --- |
| Каталог | Повтор после ручных правок; новый вариант; простой → вариативный; архив/восстановление; подтверждённое удаление; неполная страница; нулевой остаток против ошибки API; цена одного контекста |
| Публикация | Обычная/массовая/API без фото; последняя фотография; вариант с фото родителя; черновик после восстановления архива |
| Права и цены | Гость/розница/опт/менеджер; прямые URL/API; JSON-LD/фиды/кеш; смена сессии/прав; параллельная регистрация/приглашение; чужой заказ |
| Розничный срок | До/после часа; нет попыток; отменены; pending; unknown создания/статуса/снятия; waiting_for_capture; поздний успех с наличием/нехваткой |
| Оптовый срок | До/после 24 часов; подтверждение/отклонение/неизвестная проверка; гонка со снятием; новая версия состава; долгое ожидание |
| Конкуренция | Последний остаток: два заказа, розница+опт, сайт+менеджер, сайт+другой канал; таймаут; отгрузка без двойного уменьшения |
| Деньги | Намерение до POST; повтор ключа; unknown более 24 часов; повтор события; сверка; полный/частичный/ожидающий возврат |
| Доставка | РФ; устаревший пункт; город; упаковка; ошибка тарифа/лимитов; разница расхода продавца; старый/заменённый трек; обратное направление |
| Маркировка | Одежда/обувь; полные коды/разделители; одинаковые варианты с разными экземплярами; проверка/чек/вывод из оборота; повтор/возврат |
| Эксплуатация | Без посещений; сбой очереди; старая база; операции после копии; сверка перед запуском; RPO/RTO; безопасная восстановленная копия |

Управляемые часы применяются для быстрых проверок сроков. В доказательстве отдельно отмечаются имитация времени и реальность API. Нагрузочный профиль строится по фактическим данным и верхней границе каталога; параметры и результаты сохраняются.

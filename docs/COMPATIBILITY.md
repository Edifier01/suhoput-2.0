### Подготовленный сценарий после EXT-005

1. Проверить заполненность локальных полей без значений в выводе. Сверить выбранный договор/кабинет/хост, перечень **разрешённых для чтения** объектов, квоты каждой системы и окно наблюдения. Секреты не вводить в публичные формы документации. Исходные рабочие ответы не писать в Git/журналы; выбирать только необходимые поля, получателя сверять в памяти. Связь реального объекта с псевдонимом хранить отдельно локально.
2. СДЭК: авторизация → GET по точному разрешённому `cdek_number` → GET по возвращённому UUID → повтор в новом процессе. Сверить с ручной накладной/датой создания после первой авторизации. Почта: SOAP `getOperationHistory` по разрешённому Barcode → повтор в новом процессе; независимо от наличия документа в REST «Отправке». Успех авторизации/HTTP не заменяет совпадение объекта и полной доступной истории.
3. Для каждого перевозчика прочитать контрольные истории прибытия/вручения, невручения и возврата. Для СДЭК дополнительно прочитать только разрешённую связанную обратную накладную. Сверить направление и взаимные ID. Не искать произвольные рабочие отправления, не вызывать методы отказа/клиентского возврата, создания/изменения/удаления заказов. При нехватке истории критерий остаётся открытым; искусственно вызвать возврат нельзя.
4. Проверить ПВЗ/ОПС и одну выбранную договорную услугу на согласованных параметрах полного заказа. Записать входы/единицы/все доплаты, ответ и сравнение с кабинетом. EXT-006 остаётся зависимостью полной товарной упаковки TASK-032/033; для раннего расчёта нужны отдельные подтверждённые контрольные параметры.
5. Начать наблюдение **до нового обычного события** согласованного ручного отправления. Частоту/бюджет согласовать с фактическими лимитами; никакой production-интервал сейчас не назначен. Для СДЭК проверить существующую ORDER_STATUS-подписку GET-запросом и возможность чтения её локального журнала. Новая подписка/смена URL требуют отдельного согласования: создают внешнее состояние и поток данных. Без доступного приёмника webhook его задержка остаётся неизмеренной; учебная доставка JSON не заменяет реальный callback.
6. Передать в TASK-011 исходные коды/атрибуты/признаки направления, времена и границы наблюдения, отдельно от транспортной классификации. Не назначать кассовое событие/исполнителя/допустимый срок; это требует TASK-011 и внешних кассовых сведений.

СДЭК документирует порог гарантированной обработки 200 RPS, но это **не подтверждённая квота владельца**. В описании webhook — таймаут соединения 15 с, до 12 попыток за 75 минут, отключение подписок проблемного URL после исчерпания, удаление при иных неуспешных ответах через 24 часа, не более двух подписок клиента. Проверить существующее состояние, не создавать дубликаты. Гарантия задержки возникновения/публикации статуса из этих чисел не следует. ### Измерение времени и форма передачи

Каждое наблюдение имеет `probe_alias`, `carrier`, `api_version`, `transport` (poll/webhook), `request_started_at`, `response_received_at` (полностью полученный ответ), `http_or_soap_result`, `raw_status`, `raw_attribute/reason`, `raw_event_time`, `occurred_at_utc`, `first_seen_at_utc`, `direction/proof`, `deleted`, `previous_absent_observation`, `evidence_ref`, `code_sha`. CarrierEvent.received_at отражает получение конкретного события; первое наблюдение и повторы сохраняются раздельно. Идентификаторы реальных объектов — в игнорируемой локальной связи, публичный протокол использует псевдонимы.

Для SOAP источник события — `OperDate`; для СДЭК GET — `statuses[].date_time`, callback — оба документированных времени. Сохранять исходную строку/offset; переводить в UTC только при известной зоне. Время без зоны, отрицательная задержка, удалённый статус или расхождение часов отмечаются, а не исправляются догадкой. Часы локальной машины/приёмника и их синхронизацию проверить перед наблюдением; HTTP Date не является временем вручения.

`observation_delay = first_seen_at_utc − occurred_at_utc` включает задержку перевозчика, частоту опроса и сеть. Это **наблюдаемая задержка**, не чистая задержка публикации. Если перед новым событием есть успешный полный ответ без него, консервативная граница доступности — между **началом** последнего отрицательного запроса и получением первого положительного ответа (момент серверного снимка внутри запроса неизвестен). Ошибка/таймаут не являются отрицательным наблюдением. При неполной/немонотонной истории такую границу не заявлять. Старое событие, впервые прочитанное сегодня, подтверждает только историческую доступность, а не задержку его первоначальной публикации.

Отчёт после реальных проверок содержит число событий/длительность окна, пропуски/ошибки, min/max измеренной задержки и указанную неопределённость; малую выборку не объявлять SLA. Время фактической передачи из независимого разрешённого источника сохраняется отдельно от времени установки статуса. Сейчас для обоих перевозчиков измеренных транспортных событий **нет**; значения задержки отсутствуют, не равны нулю. Почтовые уведомления сайта здесь не запускались; будущие имитации писем выполняются только в Mailpit. Дубли/старые события/смена трека/фискальные эффекты в работающем адаптере — приёмка TASK-034/035, не подтверждённая этим документом.

## Состав копий и контроля

Реализация разрешённого пакета (статическая последовательность, оперативное состояние только STATUS):

1. `infra/backup/guards.py` и независимые fault tests: scope/source identity, manifest/chain, media paths, prerequisites retention и бюджет; сначала RED, затем GREEN.
2. `infra/backup/worker.py`: защищённый config/atomic receipts, независимые locks/cache/repository для base/media и minute binlog, dump+inventory/full/pre-update, native checksum, upload reconciliation и heartbeat только после подтверждения. Две repository внутри того же разрешённого prefix исключают блокировку minute lane долгой full/prune. Credentials только отдельного S3-B, subprocess argv без secret values.
3. Отдельный owner-kit: переносимая encrypted repository restic под известным владельцу новым паролем, с S3-B recovery credentials/password/manifest. Вход — защищённый локальный credential, выход — encrypted комплект; plaintext только tmpfs. Проверить независимую расшифровку без VPS/DPAPI и настоящий S3-read.
4. Только после owner-kit: защищённая установка новых backup файлов и проверенного binary, stage dump/config rollback, ROW overlay/перезапуск только stage DB с прежним image/volume. Репозиторий/ключ/данные не удалять при ошибке.
5. Настоящие S3 base/full/binlog snapshots и восстановление в новый control DB/каталог, поздние synthetic order/operation и все WordPress originals/sizes/gallery refs; negative gap/corruption/missing-media/unknown upload controls.
6. Retention30д/prerequisites, измеренные запросы/bytes/egress и сверка биллинга → только затем enable новых timers и длительные реальные срабатывания. Восемь новых файлов могут быть установлены/verified disabled, одиночный bounded manual service control не доказывает расписание. При недостающем входе сохранить цепочку и конкретный blocker; частоту/30д не ослаблять. Независимое ревью точного изменения и оба foundation точного итогового SHA обязательны.

- Hourly: транзакционный dump только stage schema, точные base file/position, полное логическое состояние uploads с передачей изменённых блоков, UTC/source-generation/instance identity, SHA/bytes. Live MariaDB datadir не заменяет dump. Сейчас61 таблица InnoDB; смена engine/DDL требует новой проверки согласованности.
- Daily full и `pre-update`: дополнительно полный WordPress/WooCommerce, собственные plugins/theme/mu-plugin и bind-mounted файлы, конфигурация и версионный манифест. Full восстанавливается без файлов рабочей площадки. Успешный pre-update receipt обязателен до существенного обновления.
- Binlog: immutable закрытые файлы, выгрузка не реже минуты, SHA/bytes, проверка checksum штатным `mariadb-binlog`, непрерывная цепочка одной generation и heartbeat **после** подтверждённого upload с сохранением времени захвата данных; позднее reconciliation не делает старый payload свежим. Lag>60с, gap/смена generation/rollback clock дают ошибку. Exit0 timer не доказывает сохранённые данные.

`mariadb-dump --single-transaction --master-data=2` — кандидат для InnoDB согласно [MariaDB dump](https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump). При изменении media во время захвата проверить согласованность, не принимать snapshot автоматически. Полная owner-проверка включает реально прочитанные и расшифрованные данные, а не только наличие объектов.

1. Зафиксировать UTC сбоя и точный target file/position с проверенной границей события/транзакции. Выбрать base до target, full с нужным кодом и media snapshot по расписанию. Недоступный target не заменять молча последней точкой. Сверить S3-B/prefix, версии и доступ owner-ключом.
2. Использовать новый пустой каталог и отдельный DB instance/volume, проверить Docker labels/image/mounts/отсутствие коллизии непосредственно перед импортом. Исходный stage и SITE-A не являются целью. До bootstrap выключить egress/внешние адаптеры/cron/AS/системную очередь, оставить `event_scheduler=OFF`; контрольная DB без публичного порта/сети приложения. Проверить host boundary; будущие synthetic письма идут в Mailpit.
3. Реально выполнить `restic check --read-data`, затем `restic restore <verified-snapshot-id> --target <new-control-directory> --verify`. Это сетевые операции с расходами и lock-файлами; ручной native контроль выполнен12.10.2026, EXEC-CHK-058. Полное независимое owner restore остаётся not_run. Проверить SHA/bytes SQL/media/кода и общую source-generation журналов. Не применять repair/unlock/forget для сокрытия ошибок. Основание — [restic restore](https://restic.readthedocs.io/en/stable/050_restore.html).
4. Импортировать dump в отдельный контрольный MariaDB10.11.19 instance. Для ROW replay сохранить исходное имя схемы **в новом instance**; переименование SQL или `--database` не являются изоляцией row events. Пароль не передавать в argv, SQL/data не выводить в отчёт.
5. Проверить каждый binlog штатным инструментом и применить непрерывную цепочку от base file/position до target. `--start-position` относится к первому файлу, `--stop-position` к последнему; сохранять один контролируемый SQL-сеанс. Для wall-clock stop отдельно подтвердить UTC/TZ и отсутствие partial transaction. Основание — [PITR](https://mariadb.com/docs/server/server-usage/backup-and-restore/mariadb-backup/point-in-time-recovery-pitr-mariadb-backup) и [binlog options](https://mariadb.com/docs/server/clients-and-utilities/logging-tools/mariadb-binlog/mariadb-binlog-options). Реальный replay двух закрытых logs после base до committed target проверен12.10.2026, EXEC-CHK-058.
6. Из восстановленной DB проверить synthetic заказ и служебную операцию **после base**, значения/уникальность/исторические ID; событие после stop должно отсутствовать. Собрать originals/`_wp_attached_file`, `_wp_attachment_metadata` (sizes/original_image), product/gallery references. Неизвестная сериализация или неполный список означает незавершённую проверку. Каждый referenced файл должен существовать внутри restored uploads и совпадать по SHA/bytes. Новый файл после последней media snapshot не считается сохранённым минутным binlog; медиа имеет hourly расписание.
7. Зафиксировать начало/конец, последний восстановленный commit/event, длительность, версии, code SHA и snapshot IDs в закрытом receipt; в ACCEPTANCE — обезличенный результат. ## Retention, ресурсы и ошибки

Сохранять точки30д и prerequisite base перед началом окна с её цепочкой; prerequisite может временно лежать сверх30д. Перед forget/prune проверить старейшую остающуюся точку реальным восстановлением. Unknown snapshots/другой источник/gap/ошибка integrity/restore/отсутствие owner-key останавливают удаление. Автоматический retention ещё не реализован. Подготовленный pure planner отклоняет gap/overlap, всегда возвращает apply_allowed=false; Boolean flags не разрешают удаление. Read-only native verifier текущего inventory/chain/конкретного anchor restore реализован, EXEC-CHK-060; native apply executor и полные prerequisites30д/restore до tip/owner/budget остаются незавершёнными. [Restic retention](https://restic.readthedocs.io/en/stable/060_forget.html) требует проверенных tags/grouping, а не слепого применения примера.

Контролировать disk/inodes/spool/cache, S3 bytes, paid requests/egress, job duration, latest successful base/full/binlog heartbeat и ошибки. Нужны согласованные RUB/GiB ceilings, тарифы, фактические счётчики и сверка биллинга. При превышении сохранить годные копии, сообщить ошибку и условие снятия в STATUS; не сокращать30д/частоту и не удалять prerequisite ради зелёного статуса. Настоящая почта alerts — TASK-046, Доставка backup alerts в Mailpit — not_run. Native мониторинг установлен: stale alert/fresh watermark проверены вручную, постоянный timer disabled.

Отдельный [архивный control](../tests/backup-archive-local.sh) действительно выполняет restic init/backup/check --read-data/restore --verify на новых синтетических текстовых файлах и media, проверяет byte equality, отказ неверного пароля и выявление намеренно повреждённого pack. Это **локальная файловая repository**, не SQL import, не binlog и не S3. Одноразовый пароль генерируется внутри tmpfs, секреты не монтируются. Запуск только в новом контейнере без сети с пустым `/control`; сначала получить официальный restic binary и проверить SHA. Пример PowerShell из корня проекта, без скачивания/установки на VPS:

## Локальная репетиция MariaDB PITR

[backup-mariadb-local.sh](../tests/backup-mariadb-local.sh) создаёт две отдельные MariaDB10.11.19 instance внутри одного нового network-none контейнера, только в пустом tmpfs. У них собственные datadir/socket, исходное имя synthetic schema одинаково; TCP и event scheduler выключены. Пароль socket-root отсутствует **только в одноразовом изолированном тесте**; такая настройка не разрешена для постоянного стенда. Контейнер не монтирует существующие тома или credentials и не открывает порты.

Сценарий делает настоящий single-transaction/master-data dump, две последующие ROW binlog, локальный encrypted restic archive/check --read-data/restore --verify и импорт в вторую DB. ## Reader и retention controls

[owner-full.php](../infra/backup/owner-full.php) получает credentials только из recovered sealed-kit, проверяет full/base/app/config/allfile SHA/complete closed logs и готовит protected artifacts. SQL import не выполняется этим PHP helper автоматически. Перед отдельной network-none DB обязательны dump schema/coordinates/SHA, [binlog.py](../infra/backup/binlog.py) и pinned native checksum/decode; после import/replay — native before/after controls и all-media reader. JSON object-key/path enumeration order нормализуется только после проверки raw manifest/hash, содержимое архивов не переписывается.

[restore.py](../infra/backup/restore.py) сохраняет прежний point profile; новый tip profile имеет отдельные fixed names и sidecars, но VPS tip objects **not_run** — вне прежнего exact list требуется конкретное согласование. Фактический archive-tip control выполнялся только локально из owner-kit. Fresh native sidecars требуют generation/token/control/base SHA/stop/replay hash/counts. Legacy point допускается при отсутствии обоих sidecars с явно ограниченным доказательством; missing/partial/tampered tip sidecars отвергаются.

[retention_apply.py](../infra/backup/retention_apply.py) — injected exact-ID executor, не готовый live CLI. Его trusted runner/store/receipt provenance и tombstone-aware retained-prefix integration ещё отсутствуют; Worker запрещает forget. Local native smoke подтверждает только restic semantics. Unknown/partial effects требуют read-only reconciliation, повтор effect и prune запрещены. Настоящая30д история и pre-window anchor не заменяются backdated fixtures. Unsupported DDL/XA/compressed/encrypted/status binlog formats fail closed; новая совместимость требует отдельного реального контроля.

## Protected native retention и сохранённый suffix

[retention_native.py](../infra/backup/retention_native.py) — отдельный root CLI `--config <protected runtime> apply|reconcile`. Он использует тот же approved STAGE-B prefix, fixed root0600 receipt paths/origin SHA, exact installed producer/code SHA и upload locks. Для nonempty batch обязательны audit, anchor, tip, owner, budget, history; CLI не принимает флаги «доказано». Audit/restore публикуют typed receipts после native controls; owner/budget/history допускаются только после фактических входов и их проверки. Отсутствие факта блокирует effect. Ноль candidates даёт NOOP с `history_coverage_accepted=false`, а не PASS30д.

До первого effect сохраняется immutable fsync intent со всеми authenticated snapshot identity rows и manifest SHA, общим source и полным списком frozen IDs. Payload lists не дублируются: полный manifest уже проверен native reader против SHA. Текущие snapshots и новые arrivals всё равно аутентифицируются; каждый preserved hourly защищает свой full. Порция до256: expired hourly/base до full; только затем original-numbered binlog prefix. Deferred expired IDs сохраняются, новая порция требует свежих proofs. Native runner допускает только точные64hex snapshot IDs выбранной lane, без prune/repair/unlock/filters.

Unknown result сохраняется и запрещает второй forget; `reconcile` читает точные present/absent IDs. Journals получают hash-bound tombstones только от protected immutable intent/receipt; original confirmed rows и binlog-chain не переписываются. Reader строит отдельный retained view, принимая только доказанный удалённый prefix; начало suffix остаётся исходным, например000002 с previous_count1. Обязательны full/base coordinates, contiguous SHA/size/CRC/ROW и anchor→target replay. Metadata forget не освобождает pack bytes; прогноз места не вычитает вымышленные prune savings.

[backup-retention-protected-local.py](../tests/backup-retention-protected-local.py) запускает actual root store/origin loader/NativeApply/restic в новых tmpfs repositories/network none. Его даты/шесть prerequisites синтетические. [backup-mariadb-local.sh](../tests/backup-mariadb-local.sh) отдельно выполняет native DB dump/checksum/ROW: forget раннего snapshot, восстановление независимого anchor и suffix, сохранение исходного archive и исключение later transaction. Эти tests не разрешают live deletion без настоящего30д окна.

## Самостоятельный launcher владельца на текущем ПК

Сохранить всю папку kit вместе с ciphertext repository и публичными helpers; пароль отдельно, в том числе в отдельном месте Google Drive. Программа не может удостоверить запуск человеком или фактическую сохранность облачной копии: это подтверждает владелец. Текущий ПК — допустимая среда, отдельная от VPS; покупка другого ПК не требуется.

Из owner-full-control запускать PowerShell7 launcher; он проверяет SHA/inventory до helper imports/запроса пароля и запускает Python в `-I -B` с пустым stdin для public preflight. При старом Windows PowerShell использовать установленный bundled pwsh7 через `& '<absolute pwsh.exe>' -NoProfile -File '.\restore-owner.ps1' -Python '<absolute python.exe>'`. Точный путь владельцу передаётся локально. Не вводить пароль в argv/env/чат. После завершения сохранить JSON из receipts, время и человеческое подтверждение. При fail сохранять все объекты/отчёт; сначала выяснить причину, не повторять SQL автоматически. Saved kit этого checkpoint остаётся неизменным.

[meter.py](../infra/backup/meter.py) читает actual Selectel UTC JSONL и считает физические строки, включая retries, HTTP method/status и transfer bytes. В export к выбранным7fields провайдер добавляет account_uuid; receipt публикует только account hash. GET billing включает HEAD, PUT включает POST/COPY; DELETE и документированные error statuses не тарифицируются за request. Provider response bytes — transport measurement; invoice quantity/rounding не подменяются ими. Бакетный CSV и source SHA сохраняются отдельно. Расход целого небольшого ручного окна или cached resume не подтверждает30д cadence и cold full restore.

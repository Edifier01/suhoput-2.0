# Копии и восстановление владельцем — TASK-047

Порядок эксплуатации и восстановления отдельного синтетического STAGE-B. Требования — [TASK-047](PLAN.md#task-047)/[SPEC](SPEC.md#почта-и-эксплуатация), внешние границы — [INFRASTRUCTURE](INFRASTRUCTURE.md#task-047-change-proposal), текущий статус — только [STATUS](STATUS.md), результаты испытаний — [ACCEPTANCE](ACCEPTANCE.md). Исторические записи ниже сохраняют контекст своих дат; действующая процедура приёмки определена [DEC-029](DECISIONS.md#dec-029).

## Процедура DEC-029

Прежние четыре новых timer/service выполняют binlog каждую минуту, базу/медиа каждый час, полную копию ежедневно в20:45UTC и monitor каждую минуту на30-й секунде. Перед существенным обновлением оператор запускает `worker.py --config <protected-runtime.json> pre-update`. Таймеры включаются после исходного бюджета. Первоначальная приёмка проверяет механизм30д на настоящем native-корпусе с явно моделируемым календарём и отдельно короткую фактическую работу STAGE-B. Даты fixture не заменяют накопленную длительность наблюдения.

Root-config `retention_readiness_policy=native-v2` включает свежие audit/anchor/tip/owner compatibility и действующий commissioning forecast. План/четыре архивных доказательства привязаны к exact frozen cohort и900с, бюджет — к расходной конфигурации и своему сроку. Legacy-v1 сохраняет прежние шесть доказательств. Возраст каждого удаляемого кандидата, anchor до границы окна, полный непрерывный suffix и подтверждённое восстановление обязательны. Прямой ввод PASS или списка IDs через CLI не поддерживается. Read-only reconciliation не вызывает повторный forget и не зависит от нового бюджета после уже совершённого эффекта.

`budget.publish_commissioning_budget(worker)` читает семь защищённых файлов `receipts/commissioning-inputs`: raw access/inventory, admission, forecast, rates, configuration, model. Проверяются исходные SHA/поля/source/generation/bucket, установленные расходные helpers/restic и восемь units. Прогноз31д содержит лимиты500RUB/10GiB, денежный резерв и рост видимых/скрытых данных; `actual_month_observed=false`, `invoice_verified=false`. Это оценка в заданных границах нагрузки, не гарантированный счёт Selectel. Исходная billing/inventory admission свежая≤24ч. Истечение срока, изменение расходного кода/расписания или рост вне модели требуют новой калибровки.

После публикации прогноз проверяется перед созданием upload authority. Копия включает в лимит настоящий raw manifest: hourly≤384KiB, full/pre-update≤192MiB, binlog≤64MiB. Все переменные base bytes вместе≤384KiB; постоянными считаются только приложение/пять конфигурационных файлов с точной authenticated application/config identity и полный набор23 recovery helpers с совпадающими SHA/размерами из `capture_policy`. Переменных файлов base≤22. В full/pre-update допускаются только db.sql, media.json, .capture.json и две точные одинаковые по path/bytes/SHA копии media; иной даже маленький файл блокируется. Это ограничивает выбор различных data packs при восстановлении. Для binlog manifest и служебные файлы вместе≤2KiB. Источник за последние24ч, logdata текущего payload и сумма данных подтверждённых snapshots за24ч каждое ограничены2MiB. Подтверждения берутся из exact finalized chain/journal с полной ID-set equality; старое время захвата или mtime не скрывает недавно отправленный backlog. Повторная сверка уже подтверждённого manifest не считает его второй раз. Manifest отдельно≤64KiB/hourly,2MiB/full,2KiB/binlog; консервативные native tree bounds≤64KiB/hourly,9MiB/full,8KiB/binlog учитывают пустые directories, UTF8/JSON escaping, минимальный chunk512KiB и фиксированные root/no-xattr ancestors. Несовпадение, изменение helpers/application или превышение сохраняет payload и требует пересчёта перед загрузкой. Pure `validate_capture_geometry` используется для калибровки и сама бюджет не принимает. Первые ручные controls при отсутствии report и origin остаются до admission; наличие хотя бы одного из них требует полной проверки пары.

Если у исторического provider export нет полного SHA расходной конфигурации, он остаётся `observed_configuration_sha256=null`, `current_configuration_observed=false`. Отдельный protected `historical-baseline-review-v1` связывает точные provider/model/target hashes и проверенные raw receipts пяти текущих controls: archive roundtrip, index compaction, restore, retention, visible inventory. Installer проверяет реальные результаты этих controls до admission; ссылки SHA сами по себе не являются доказательством. Model содержит тот же набор ссылок. Старый экспорт не получает новую дату или мнимую привязку к новому коду; legacy mismatch без отдельного review блокируется.

Monitor проверяет нагрузку каждую минуту, полный ListObjectsV2 бакета для forecast v3 кэширует менее6ч с настоящим временем чтения. Оценка сохраняет весь первоначальный billed-total, видимый снимок, metadata4KiB/объект, запас шестичасового роста bytes/objects/indexes и будущего скрытого хранения. CSV не объявляется текущей полной инвентаризацией; ListObjects не доказывает отсутствие versions/multipart. Ежедневная ручная CSV не нужна. Защищённый `commissioning-live.json` с давностью≤120с используется перед каждой изменяющей фазой retention без сети под upload locks.

Native-v2 `retention_native.py ... apply` обрабатывает суточный intent до1536 проверенных snapshots командами не более256 и публикует журналы. Перед каждой командой повторяются guards в исходном900с окне; locks отпускаются между командами. Отдельный `Maintenance(worker).run(lane)` выполняет zero-repack prune, сохраняя repository identity и весь snapshot set; durable intent предшествует эффекту. Видимая физическая разница измеряется S3 ListObjects, затем выполняется uncached read-data. `operation='compact'` выполняет отдельный index repair и metadata check; он не обновляет дату полной проверки. Unknown сохраняет intent/native lock; `reconcile` только читает состояние, автоматического retry/unlock нет. Наличие команды само по себе не доказывает месячную стоимость.

Обслуживание retention выполняет оператор проекта ежедневно с новым frozen cohort и свежими anchor/tip control restores. Это отдельный запуск, не скрытое действие четырёх backup timers. Полный uncached контроль целостности выполняется минимум еженедельно и после физической очистки; до истечения7д audit/owner используют его неизменную дату и защищённую карту identities, проверяя новые admissions и доказанные retirements. Monitor не продлевает этот срок. Плановые restores используют текущие S3 base/full и проверенные ROW/CRC байты каталога; новый контрольный DB после проверки останавливается, его данные сохраняются. Выход за ограничения приводит к ошибке с сохранением последней годной цепочки: сокращать30д или пропускать обязательные копии ради PASS нельзя.

## Независимый комплект владельца

Нужны защищённые endpoint/region/bucket/prefix S3-B, отдельный S3-B credential, **новый** recovery password репозитория, проверенный официальный restic binary/его SHA-256, SHA приложения и манифест компонентов. S3 credential не заменяет пароль расшифровки. Копия пароля только на VPS или внутри самого репозитория недостаточна. Прежний backup-key/password не используются.

DPAPI credential привязан к текущему Windows-профилю. Владелец подтвердил отдельное хранение переносимого комплекта и пароля в Google Drive и самостоятельное успешное восстановление12.10.2026 16:27–16:29UTC на этом ПК без VPS/DPAPI. Другой физический компьютер — not_run; покупка не требуется. Полный receipt и версия комплекта — [ACCEPTANCE](ACCEPTANCE.md#exec-chk-061). Секреты не передавать в чат, Git, PR, receipt или argv. Серверные credential/password files — root0600 в root0700 каталоге. Проверять происхождение/права, читать env как данные, не исполнять его как shell-код.

Кандидат — [restic0.19.1](https://restic.net/blog/2026-07-05/restic-0.19.1-released/), repository format2, проверка TLS/hostname и path-style S3. Документация [repository/S3](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html) изучена11.10.2026. Официальный binary скачан локально, SHA-256 совпал с Release SHA256SUMS. 12.10.2026 подпись SHA256SUMS проверена GPGV2.4.9 с fingerprint из [официальной инструкции](https://restic.readthedocs.io/en/stable/020_installation.html#stable-releases); изменённый manifest отвергнут. Локальные архивирование и MariaDB replay испытаны, EXEC-CHK-054. Совместимость restic с S3-B проверена реальными synthetic upload/read/integrity/restore, EXEC-CHK-055. На VPS проверенный binary установлен12.10.2026; native controls — EXEC-CHK-058. Независимая расшифровка owner-комплекта/чтение synthetic S3 archive проверены EXEC-CHK-056; Полное восстановление владельцем позднее выполнено12.10.2026, EXEC-CHK-061.

[owner-kit.php](../infra/backup/owner-kit.php) создаёт отдельную зашифрованную repository format2 под новым паролем владельца. Внутри — S3-B scopes/credential, новый recovery password репозиториев, preparation Git SHA/generation и authenticated manifest. Снаружи — проверенный restic Linux amd64, SHA256SUMS, helper/инструкция и точный kit snapshot ID. Секреты поступают только через stdin; builder/recovery работают в0700 tmpfs/0600 files, stdout/stderr native commands остаются там. Выход — ciphertext repository и публичные инструменты. Точный защищённый путь/ID/receipts хранятся ignored `.cache/infrastructure/task047-owner-kit-creation-20261012-B.local.json`; пароль шифрования самого owner-kit не лежит в payload.

Владелец сохраняет **всю** папку комплекта на независимый носитель и пароль отдельно. Использовать RESTORE-OWNER.txt из комплекта: проверить SHA256SUMS, в новом Linux tmpfs создать0600 password file, выполнить `restic --repo <kit>/repository --password-file <tmpfs>/password --no-lock check --read-data`, затем `restore <exact kit snapshot> --target <tmpfs>/restored --verify`. Не печатать recovery.json: он содержит S3 credential/password. На момент создания kit base/binlog URLs ещё не были initialized;12.10.2026 runtime создал repository format2, независимый reader проверил новые manifests. Путь `preparation_code_sha` обозначает версию подготовки kit, не работающую версию приложения STAGE-B.

Реальные проверки этого комплекта: init/backup/check, отдельный reader без VPS/DPAPI, wrong-password отказ и S3 check/cat exact snapshot/dump controls; ещё один reader использовал **файлы сохранённой папки**, не память creator. Это owner-key portability, не восстановление полного WordPress и не испытание на другом физическом компьютере. [backup-owner-kit-native.php](../tests/backup-owner-kit-native.php) в CI повторяет только local crypto на synthetic credentials, network none, wrong key/corrupt disposable pack negatives. Реальный S3 в CI не запускается.

## Состав копий и контроля

Реализация разрешённого пакета (статическая последовательность, оперативное состояние только STATUS):

1. `infra/backup/guards.py` и независимые fault tests: scope/source identity, manifest/chain, media paths, prerequisites retention и бюджет; сначала RED, затем GREEN.
2. `infra/backup/worker.py`: защищённый config/atomic receipts, независимые locks/cache/repository для base/media и minute binlog, dump+inventory/full/pre-update, native checksum, upload reconciliation и heartbeat только после подтверждения. Две repository внутри того же разрешённого prefix исключают блокировку minute lane долгой full/prune. Credentials только отдельного S3-B, subprocess argv без secret values.
3. Отдельный owner-kit: переносимая encrypted repository restic под известным владельцу новым паролем, с S3-B recovery credentials/password/manifest. Вход — защищённый локальный credential, выход — encrypted комплект; plaintext только tmpfs. Проверить независимую расшифровку без VPS/DPAPI и настоящий S3-read.
4. Только после owner-kit: защищённая установка новых backup файлов и проверенного binary, stage dump/config rollback, ROW overlay/перезапуск только stage DB с прежним image/volume. Репозиторий/ключ/данные не удалять при ошибке.
5. Настоящие S3 base/full/binlog snapshots и восстановление в новый control DB/каталог, поздние synthetic order/operation и все WordPress originals/sizes/gallery refs; negative gap/corruption/missing-media/unknown upload controls.
6. Retention30д/prerequisites, измеренные запросы/bytes/egress и сверка биллинга → только затем enable новых timers и длительные реальные срабатывания. Восемь новых файлов могут быть установлены/verified disabled, одиночный bounded manual service control не доказывает расписание. При недостающем входе сохранить цепочку и конкретный blocker; частоту/30д не ослаблять. Независимое ревью точного изменения и оба foundation точного итогового SHA обязательны.

- Hourly: транзакционный dump только stage schema, точные base file/position, полное логическое состояние uploads с передачей изменённых блоков, UTC/source-generation/instance identity, SHA/bytes. Live MariaDB datadir не заменяет dump. Сейчас61 таблица InnoDB; смена engine/DDL требует новой проверки согласованности.
- Daily full и `pre-update`: дополнительно полный WordPress/WooCommerce, собственные plugins/theme/mu-plugin и bind-mounted файлы, конфигурация и версионный манифест. Full восстанавливается без файлов рабочей площадки. Успешный pre-update receipt обязателен до существенного обновления.
- Binlog: immutable закрытые файлы, выгрузка не реже минуты, SHA/bytes, проверка checksum штатным `mariadb-binlog`, непрерывная цепочка одной generation и heartbeat **после** подтверждённого upload с сохранением времени захвата данных; позднее reconciliation не делает старый payload свежим. Lag>60с, gap/смена generation/rollback clock дают ошибку. Exit0 timer не доказывает сохранённые данные.

`mariadb-dump --single-transaction --master-data=2` — кандидат для InnoDB согласно [MariaDB dump](https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump). При изменении media во время захвата проверить согласованность, не принимать snapshot автоматически. Полная owner-проверка включает реально прочитанные и расшифрованные данные, а не только наличие объектов.

## Восстановление в контрольный контур

1. Зафиксировать UTC сбоя и точный target file/position с проверенной границей события/транзакции. Выбрать base до target, full с нужным кодом и media snapshot по расписанию. Недоступный target не заменять молча последней точкой. Сверить S3-B/prefix, версии и доступ owner-ключом.
2. Использовать новый пустой каталог и отдельный DB instance/volume, проверить Docker labels/image/mounts/отсутствие коллизии непосредственно перед импортом. Исходный stage и SITE-A не являются целью. До bootstrap выключить egress/внешние адаптеры/cron/AS/системную очередь, оставить `event_scheduler=OFF`; контрольная DB без публичного порта/сети приложения. Проверить host boundary; будущие synthetic письма идут в Mailpit.
3. Реально выполнить `restic check --read-data`, затем `restic restore <verified-snapshot-id> --target <new-control-directory> --verify`. Это сетевые операции с расходами и lock-файлами; ручной native контроль выполнен12.10.2026, EXEC-CHK-058. Полное независимое owner restore выполнено12.10.2026, EXEC-CHK-061. Проверить SHA/bytes SQL/media/кода и общую source-generation журналов. Не применять repair/unlock/forget для сокрытия ошибок. Основание — [restic restore](https://restic.readthedocs.io/en/stable/050_restore.html).
4. Импортировать dump в отдельный контрольный MariaDB10.11.19 instance. Для ROW replay сохранить исходное имя схемы **в новом instance**; переименование SQL или `--database` не являются изоляцией row events. Пароль не передавать в argv, SQL/data не выводить в отчёт.
5. Проверить каждый binlog штатным инструментом и применить непрерывную цепочку от base file/position до target. `--start-position` относится к первому файлу, `--stop-position` к последнему; сохранять один контролируемый SQL-сеанс. Для wall-clock stop отдельно подтвердить UTC/TZ и отсутствие partial transaction. Основание — [PITR](https://mariadb.com/docs/server/server-usage/backup-and-restore/mariadb-backup/point-in-time-recovery-pitr-mariadb-backup) и [binlog options](https://mariadb.com/docs/server/clients-and-utilities/logging-tools/mariadb-binlog/mariadb-binlog-options). Реальный replay двух закрытых logs после base до committed target проверен12.10.2026, EXEC-CHK-058.
6. Из восстановленной DB проверить synthetic заказ и служебную операцию **после base**, значения/уникальность/исторические ID; событие после stop должно отсутствовать. Собрать originals/`_wp_attached_file`, `_wp_attachment_metadata` (sizes/original_image), product/gallery references. Неизвестная сериализация или неполный список означает незавершённую проверку. Каждый referenced файл должен существовать внутри restored uploads и совпадать по SHA/bytes. Новый файл после последней media snapshot не считается сохранённым минутным binlog; медиа имеет hourly расписание.
7. Зафиксировать начало/конец, последний восстановленный commit/event, длительность, версии, code SHA и snapshot IDs в закрытом receipt; в ACCEPTANCE — обезличенный результат. Оставить контрольный контур закрытым. Сверка внешних связей/денег/резервов, старая очередь и общие RPO≤5мин/RTO≤4ч сервиса — [TASK-048](PLAN.md#task-048)/TASK-054, этим протоколом не закрыты.

## Retention, ресурсы и ошибки

Сохранять точки30д и prerequisite base перед началом окна с её цепочкой; prerequisite может временно лежать сверх30д. Перед forget/prune проверить старейшую остающуюся точку реальным восстановлением. Unknown snapshots/другой источник/gap/ошибка integrity/restore/отсутствие owner-key останавливают удаление. Автоматический retention ещё не реализован. Подготовленный pure planner отклоняет gap/overlap, всегда возвращает apply_allowed=false; Boolean flags не разрешают удаление. Read-only native verifier текущего inventory/chain/конкретного anchor restore реализован, EXEC-CHK-060; native apply executor и полные prerequisites30д/restore до tip/owner/budget остаются незавершёнными. [Restic retention](https://restic.readthedocs.io/en/stable/060_forget.html) требует проверенных tags/grouping, а не слепого применения примера.

Контролировать disk/inodes/spool/cache, S3 bytes, paid requests/egress, job duration, latest successful base/full/binlog heartbeat и ошибки. Нужны согласованные RUB/GiB ceilings, тарифы, фактические счётчики и сверка биллинга. При превышении сохранить годные копии, сообщить ошибку и условие снятия в STATUS; не сокращать30д/частоту и не удалять prerequisite ради зелёного статуса. Настоящая почта alerts — TASK-046, Доставка backup alerts в Mailpit — not_run. Native мониторинг установлен: stale alert/fresh watermark проверены вручную, постоянный timer disabled.

## Локальные проверки

`python3 tests/backup_model_test.py` выполняет только synthetic сценарии. Подготовленный `tools/backup_model.py` читает локальный JSON/каталог и не меняет DB/S3:

```text
python3 tools/backup_model.py chain <local-chain-evidence.json>
python3 tools/backup_model.py files <local-inventory.json> --root <isolated-restored-directory>
python3 tools/backup_model.py retention <local-snapshot-evidence.json>
python3 tools/backup_model.py cost <local-month-projection.json>
```

Формат входов — fixtures в [тестах](../tests/backup_model_test.py).

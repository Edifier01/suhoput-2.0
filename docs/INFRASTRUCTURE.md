## Обследование без изменений

Для serial web-console вводить короткие команды; при необходимости разбивать ввод на небольшие части и нажимать Enter только после полного набора. При сбое ввода сначала отменить/очистить строку и визуально подтвердить чистое приглашение. Вывод службы/таймеров получать с `--no-pager`; если открыт pager, выйти из него и подтвердить shell до следующей команды. Прерванный ввод без Enter, команда в pager и исполненная команда без сохранённого результата не являются успешными доказательствами. Не читать полный DOM-снимок страницы консоли: адрес встроенного сеанса может содержать временный токен; использовать экран и узко выбранное поле ввода.

Входы — [ACCESS](ACCESS.md#infrastructure-inputs). Работать только с подтверждёнными объектами. Каждый результат записывать с UTC начала/получения, датой Europe/Moscow, командой без значений секретов, версией клиента/сервера, окружением, SHA кода и итогом. `not_run`, `access_denied`, `unsupported` и `observed` различаются. Отсутствие доступа не означает отсутствие ресурса.

1. Проверить форму локально, показывая только имена полей и заполненность. Секреты не source/dot-source как код; не печатать env, токены, private keys или полную конфигурацию. Сверить целевой VPS/бакет/домен и границы чтения по сведениям владельца. Не извлекать случайные цели из known_hosts и не искать пароли по личным папкам.
2. Сверить SSH host fingerprint через доверенный канал владельца/панель и соответствующую запись known_hosts. SSH — `StrictHostKeyChecking=yes`, без agent forwarding, туннелей и принятия неизвестного ключа. Начать с коротких команд. Для уже настроенного ключа использовать `BatchMode=yes`, `IdentitiesOnly=yes`, `ConnectTimeout=10`; при другом способе входа сначала определить безопасный ввод без передачи пароля в командную строку/отчёт. Не менять сервер ради подключения. Существующая запись known_hosts и отдельная независимая сверка fingerprint — разные доказательства. При зашифрованном ключе проверить только разрешённый владельцем локальный источник фразы в памяти; ошибку зависимости декодера отличать от неверной фразы. Не сохранять расшифрованный private key, не менять его фразу и не пробовать её как пароль сервера.
3. Снять версию ОС/ядра, CPU/RAM, файловые системы/свободное место/inodes, текущую нагрузку и синхронизацию часов. Подготовленные Linux-команды ниже запускаются отдельно, только после подтверждения цели. Отсутствующий инструмент или отказ права записать; ничего не устанавливать, не запускать нагрузочную проверку и не менять часовой пояс.

```sh
date -u +%Y-%m-%dT%H:%M:%SZ
id -u
uname -srm
cat /etc/os-release
nproc
free -b
df -PT
df -Pi
uptime
timedatectl show --property=Timezone --property=NTPSynchronized
ss -lnt
systemctl list-units --type=service --all --no-pager
systemctl list-timers --all --no-pager
```

4. Выяснить существующие сайты/БД, владельцев каталогов, web/PHP/DB версии, панель/контейнеры, задания и действующие копии через метаданные и разрешённые сведения владельца. Выполнять только версии установленного стека (`nginx -v`, `apache2 -v`, `php -v`, `php -m`, `mariadb --version` по наличию). Каталоги/БД в приватной записи связывать с метками сайта; публичный отчёт не содержит адресов доступа, имён учёток/бакетов или рабочих данных. Не выполнять `nginx -T`, полные `docker inspect`/env, `systemctl status` с журналами, вывод crontab/секретных конфигов. Не загружать рабочий WordPress через WP-CLI/HTTP ради инвентаризации: плагины/cron могут иметь побочные действия. В случае нехватки метаданных запросить узкую обезличенную выборку владельца.
5. При уже существующем разрешённом доступе к DB читать только метаданные, без бизнес-строк/дампа. Список доступных схем и версии получить через панель или ограниченного пользователя. Кандидат SQL для проверки возможностей, не выполненный сейчас: `SHOW VARIABLES WHERE Variable_name IN ('version','version_comment','log_bin','binlog_format','binlog_expire_logs_seconds','expire_logs_days','time_zone','system_time_zone','read_only');`. Отсутствующее поле помечать unknown; настройку binlog не менять. SQL-метаданные не доказывают RPO/RTO.
6. Для выбранного S3-бакета подготовлены HEAD Bucket, GET Location/Versioning/Policy в пределах действующих прав. Предпочтителен SDK с Signature v4, проверкой TLS и выбранным endpoint/регионом; версию инструмента записать при выполнении. AWS CLI локально не обнаружен — это не запрет другого согласованного клиента. Не перечислять все бакеты аккаунта, не читать содержимое резервных копий/объектов; при необходимости только согласованный prefix и обезличенные размеры/счётчики. Никаких PUT/DELETE, тестовой загрузки, смены типа/политики/версий/retention или создания новых ключей. Ошибку 403/404 разбирать с владельцем без расширения прав и перебора объектов.
7. Для подтверждённого домена прочитать NS, A/AAAA/CNAME, MX и TXT (SPF, `_dmarc`, подтверждённый `<selector>._domainkey`); например, `Resolve-DnsName -Name '<подтверждённое имя>' -Type NS` и отдельные запросы нужного типа. Не подставлять пример домена и не менять зону. При согласованном HTTPS-адресе исследовать только TLS handshake/сертификат (имя, цепь, срок), без GET страниц магазина и без ACME-заявки. Просмотр конфигурации почтовой услуги не включает AUTH, чтение ящика или отправку письма. DNS/сертификат/параметры SMTP не доказывают доставку.

Сырой материал — только в защищённом локальном каталоге вне Git, например `.cache/infrastructure`; запрет на публикацию секретов действует и там. Перед общим отчётом удалить/заменить адреса доступа, идентификаторы аккаунтов, данные клиентов и случайно полученные секреты. Полные серверные логи/дампы не собирать. Измерение отражает момент наблюдения, не постоянную гарантию состояния. Полноценный аудит безопасности инфраструктуры этим протоколом не заявляется.

S3 endpoint для подтверждённого пула сверять по [списку URL](https://docs.selectel.ru/api/urls/#s3), не по адресу панели или ссылки на объект. Поле prefix — путь существующих объектов внутри бакета; пустое значение не разрешает полный обход. Ограниченный корневой List с delimiter/max-keys допустим только при отдельном разрешении владельца на поиск этого пути. S3 credentials сохраняются только в ignored local; [Secret key после закрытия окна выдачи нельзя посмотреть повторно](https://docs.selectel.ru/access-control/manage/edit-user-data-or-role/). Ключи не вносить в versioned example. При TLS-отказе сначала установить причину; не отключать проверку. Существующее системное доверие клиента можно использовать с сохранением проверки цепи/имени; смена доверенных корней не подразумевается.

## Подготовка отдельного стенда после обследования

До создания представить конкретный план: целевой сервер и ресурсы, hostname, каталог, отдельная БД/учётка, web/PHP конфигурация, HTTPS/доступ менеджера, сетевые границы, способ доставки артефакта, допустимые операции/окно и откат без затрагивания существующих сайтов. Кандидаты формы не являются согласованием. Если ресурсы недостаточны, описать ограничение и вариант; требования SPEC не снижать.

Сначала безопасные синтетические данные и новая отдельная база. Реальная копия возможна лишь по отдельному определённому сценарию с обезличиванием. До первого запуска PHP/WordPress закрыть внешний egress приложения и исходящие адаптеры, убрать рабочие ключи, перехватить почту в Mailpit, не запускать восстановленные cron/AS/system queue. Проверить, что наследуемые pending-задачи и SMTP-плагины не обходят границу. Панель Mailpit/DB не публиковать наружу. SSH администрирования не является доступом приложения к API.

Локальный `infra/compose.yaml` — свидетельство реализованной локальной основы, не готовый способ безопасной установки на VPS. Его mounts, loopback-порты и сетевую изоляцию нельзя переносить без проверки фактического стека. `WP_ENVIRONMENT_TYPE=staging` сам не блокирует исходящие действия. Адаптацию/установку выполнять только после обследования и согласования; этот протокол конфигурацию сервера не меняет.

Приёмка TASK-044: фактические Timeweb/Selectel/DNS/почта и доступы обследованы; существующие сайты/БД и ресурсы учтены; конкретные каталог/БД согласованы; отдельный стенд существует и доступен только предусмотренным лицам; доказана изоляция писем/денег/кассы/склада и старой очереди в целевой среде. Блокированные HTTP/SMTP/очередь и Mailpit проверить на безопасных данных без обращения к рабочим API. Зафиксировать версии, SHA и результаты; TASK-044 не становится done по одной документации. Release-пайплайн, доставка рабочей почты/системные задания, копии/RPO/RTO и нагрузка остаются соответственно TASK-045–049; ЮKassa — последний этап.

## Согласованная схема отдельного размещения

11.10.2026. **Схема согласована владельцем, VPS-конфигурация установлена и испытана: [EXEC-CHK-045](ACCEPTANCE.md#exec-chk-045), [EXEC-CHK-046](ACCEPTANCE.md#exec-chk-046). Изоляция отдельного S3-доступа ещё не подтверждена.** Источник и точные границы — [DEC-024](DECISIONS.md#dec-024). Это адаптация существующей локальной контейнерной схемы; утверждённые SPEC/PLAN и кассовая/складская архитектура не меняются. Конкретные private объекты собраны для просмотра владельцем в ignored `.cache/infrastructure/change-objects-20261011.local.md`; не копировать этот пакет в публичный PR. Причина отдельного размещения: существующие PHP-FPM/сайт/БД и старые каталоги не переиспользуются для исполнения нового кода.

Выбранный вариант — новая Compose-группа STAGE-B на обследованном VPS, собственные volumes/БД `suhoput2_stage`, WordPress/PHP/WooCommerce/MariaDB по закреплённым локальным версиям/digests. Новый каталог, лимит памяти всего проекта до 3 GiB и CPU до 2 ядер, без рабочей БД/медиа/секретов, только синтетические данные. Размещение через общие рабочие PHP/MariaDB службы потребовало бы изменений рабочего runtime и не применяется.

Разрешённый первый шаг выполнен: public key добавлен **только существующей административной учётке**, старые байты и режимы сохранены, две свежие SSH-сессии успешны, [EXEC-CHK-042](ACCEPTANCE.md#exec-chk-042). Root/password SSH и sudo-права не расширены. На момент EXEC-CHK-043 новая конфигурация Docker/Compose ещё не была установлена: новая системная служба и сетевые правила являются реальными host-изменениями. До установки проверить полный необходимый набор конфликтующих пакетов, маршруты и правила, выбрать конкретные подписанные официальные версии и сохранить метаданные исходного состояния; не удалять старые пакеты/данные автоматически. Определён существующий статический CSS, который по проверенным nginx location/path не запускает PHP/WordPress; HTTPS GET до host-изменений возвращает **503**, не файл. Root-консоль подтвердила существующий WRITE_DISABLED; nginx настроен возвращать 503 при его наличии. Тогда без успешного baseline установка была остановлена, [EXEC-CHK-043](ACCEPTANCE.md#exec-chk-043). После диагностики и выбора владельца сохраняется прежнее закрытое состояние; адаптированная проверка описана ниже. Сравнить его статус/TLS/marker/службы/содержимое до и после установки. При отсутствии/изменении результата, конфликте или невозможности безопасного отката остановиться и согласовать узкое следующее действие; сохранность метаданных сама не доказывает доступность сайта.

Приложение/БД/Mailpit находятся во внутренней сети без внешнего egress; только отдельный proxy имеет вход. Публикация proxy — **127.0.0.1:18890** (WP) и **127.0.0.1:18891** (Mailpit), БД/SMTP наружу не публикуются, Docker socket и рабочие каталоги в приложение не монтируются. Доступ первого этапа только владельцу по SSH-туннелю с закреплённым host trust; это частный HTTP внутри шифрованного SSH, **не новая публичная HTTPS-точка**. Внешний hostname/HTTPS и доступ другим лицам требуют следующего конкретного плана. Существующие nginx, PHP-FPM, MariaDB, 80/443 и DNS не перенастраиваются/не перезапускаются. Установку Docker/UFW обязательно проверить фактически: loopback binding и слово internal сами не доказывают изоляцию.

Перед первым bootstrap монтируется read-only guard внешних HTTP/почты, внешние записи выключены, wp-cron/AS async/system worker не стартуют, нет рабочих ключей и унаследованной очереди. Архив подготовки привязан к проверенному SHA/SHA-256 и передаётся по SSH; production/release pipeline TASK-045 не объявляется готовым и GitHub Release сейчас не выпускается. Конфигурация `infra/staging/compose.yaml`, guard и локальный suite реализованы и испытаны на новых синтетических томах; [EXEC-CHK-045](ACCEPTANCE.md#exec-chk-045).

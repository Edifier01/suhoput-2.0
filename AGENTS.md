# Правила работы агента

Проект Suhoput 2.0 разрабатывается в Codex. Рабочая папка, Git, терминал и доступные средства проверки достаточны; процесс не зависит от VS Code. Требуемый результат определён в [SPEC](docs/SPEC.md).

## Начало работы

1. Прочитать этот файл и [STATUS](docs/STATUS.md).
2. Проверить ветку, `git status --short --branch`, подготовленные и неподготовленные изменения. Не удалять и не перезаписывать чужую незавершённую работу.
3. Найти текущую задачу в [PLAN](docs/PLAN.md), затем прочитать связанные требования, архитектуру, решения и приёмку. Пока PLAN не составлен, работать над подготовкой/планированием, указанными в STATUS; функциональную разработку не начинать.
4. Сопоставить записи с реальными файлами и кодом. При первичном планировании прочитать SPEC полностью. Повторный аудит всего проекта нужен при конкретной причине, а не при каждом новом агенте.
5. До изменения файлов обновить текущую задачу в STATUS. При передаче оставить точное место остановки и следующее действие.

## Назначение документов

| Документ | Единственный основной источник |
| --- | --- |
| [SPEC](docs/SPEC.md) | Требуемый результат, полный текст ТЗ и идентификаторы требований |
| [ARCHITECTURE](docs/ARCHITECTURE.md) | Устройство, границы и технические вопросы |
| [PLAN](docs/PLAN.md) | Результаты задач, зависимости и последовательность; оперативный статус здесь не хранится |
| [STATUS](docs/STATUS.md) | Текущее состояние, препятствия, незавершённые изменения и передача работы |
| [ACCEPTANCE](docs/ACCEPTANCE.md) | Покрытие требований и доказательства проверок |
| [DECISIONS](docs/DECISIONS.md) | Значимые решения, основания и источники согласования |
| [README](README.md) | Окружение, запуск и способы проверки |

Факт, предложение, допущение и непроверенная возможность обозначаются явно. Другие документы ссылаются на основной источник; несколько независимых списков текущих задач не вести. Необязательные улучшения учитывать в STATUS. Новый документ создавать только при самостоятельном назначении.

## Обязательные границы

- WordPress и WooCommerce; собственная классическая тема и отдельные плагины правил магазина и МойСклад. Классические корзина и оформление, WooCommerce CRUD API и совместимость собственных плагинов с HPOS. Внешний API не вызывается из шаблонов темы; сторонние модули не редактируются.
- Владение полями определяется SPEC. Повторный обмен сохраняет ручные правки сайта, публикацию и исторические связи; источником ключей служат устойчивые ID.
- Розница и опт имеют раздельные права и цены, общий контур остатков/резервов и разные процессы заказа. Состояния оплаты, исполнения, доставки, резерва и обмена независимы. Одно событие имеет одного исполнителя и не дублирует резерв, письмо, деньги или чек.
- Коды маркировки сканируются в МойСклад при отгрузке. Полнота кодов, сопоставление экземпляров и поддержка выбранного пути должны быть доказаны. Повторное сканирование, ручной перенос и собственная замена разрешительной проверки не добавляются без отдельного решения.
- **Установка, подключение и интеграционные испытания ЮKassa выполняются последними**, после остальных функций и определения кассовой схемы. Ранее допустимы интерфейсы и имитации платёжных событий в изолированной среде; документацию и исходники выбранной версии можно изучать заранее.
- Сведения о ККТ, ФН, кассовом ПО, ОФД, регистрации и подключении интернет-заказов запрашиваются перед зависимой фискальной частью. Их отсутствие не останавливает независимую работу.
- Согласованные бизнес-решения не обсуждать повторно без конкретного противоречия или доказанного ограничения. При ограничении описать влияние и поддерживаемую альтернативу, получить согласование изменения; независимые задачи продолжать. Новые функции требуют отдельной задачи.
- Соблюдать все остальные ограничения SPEC, включая отсутствие купонов/личных скидок, единую полную отправку, ручной оптовый ЭДО СБИС и запрет автоматического возврата из-за нехватки товара.
- Локальное окружение, стенд и production разделены. Секреты и рабочие персональные данные не входят в Git и отчёты. Копия рабочего сайта по умолчанию не отправляет реальные письма и не выполняет боевые денежные, кассовые и складские операции.
- Выпуск: проверенный GitHub Release с commit SHA и SHA-256, передача архива по SSH; `git clone` на production не применяется. Секреты задаются в целевом окружении. До работы на сервере изучить его фактическое состояние.

## Выполнение и проверка

Одна задача имеет ограниченный объём, наблюдаемый результат и критерии завершения. В её пределах агент самостоятельно реализует, проверяет и исправляет подтверждённые дефекты. Git используется с начала работы, изменения сохраняются понятными контрольными точками; ветки, ревью и CI применяются соразмерно задаче. Не придумывать автора коммита или хеш ещё не созданного коммита.

Параллельная работа допустима для независимых задач с разделением файлов, рабочих копий и изменяемых данных. Общий результат имеет одного ответственного исполнителя.

Проверки выбирать по изменению и риску: работающий WordPress, бизнес-правила, интерфейс, внешние интеграции, эксплуатация. Ревью относится к определённому изменению и версии; замечание содержит сценарий, место в коде и последствия. Существенные подтверждённые дефекты исправляются, улучшения учитываются отдельно. Повторять проверки при обязательном критерии, изменении поведения или конкретном нерешённом риске.

Проверки нельзя ослаблять ради успешного статуса. Ошибку теста исправлять с объяснением и доказательством. Наличие ссылки на API не доказывает совместимость: после изучения записать дату, проверенную версию и конкретный вывод, отдельно подтвердить контрольным сценарием нужную возможность.

Для доказательства записывать дату, команду/сценарий, результат, окружение и версию кода. Различать реальные внешние испытания, имитации, ручные проверки и незапущенные проверки. Если рабочая копия отличается от коммита, указать это. После изменения поведения повторить затронутую проверку либо отметить отсутствие актуального подтверждения.

## Состояния и обновления

Состояния задач в STATUS: `not_started` → `in_progress` → `ready_for_review` → `done`. `blocked` означает конкретное препятствие с условием снятия; при его устранении задача возвращается в `in_progress`. Из ревью задача возвращается в работу при существенном замечании. `done` допустим только после выполнения критериев, устранения существенных замечаний, обязательных проверок и обновления документов. Готовность документов не означает готовность функций или выпуска.

| Событие | Обновление до завершения/передачи задачи |
| --- | --- |
| Начало, существенное препятствие, смена следующего шага | STATUS; препятствие и условие его снятия записать сразу |
| Подтверждённое изменение архитектурного решения | ARCHITECTURE и DECISIONS |
| Согласованное изменение требования | SPEC, DECISIONS и затронутые PLAN/ACCEPTANCE; SPEC содержит действующее требование |
| Изменение запуска, окружения или проверок | README |
| Завершение | Доказательства в ACCEPTANCE, фактический результат в STATUS |
| Передача | STATUS: место остановки, незавершённые изменения, требуемое следующее действие и проверки |

Текущую передачу держать короткой, историю отделять. Подробные логи при необходимости хранить отдельно со ссылкой. Все документы после каждого сообщения формально не обновлять. Выпуск требует кода, обязательных внешних действий, инструкций, проверенного восстановления и финальной приёмки по SPEC.
